Professional Self Assessment

This course marks the final step in my journey for my bachelor’s degree in software engineering at Southern New Hampshire University. After I completed my associate degree and started working towards the bachelor’s, I’ve become a lot more interested in how an application’s interface, logic, and the data work together. This portfolio should capture that interest through my animal shelter dashboard. It should also show how I’ve learned to explain my decisions and check whether a change actually does what I was intending.

I would say that my biggest improvement has been trying to look past at whether a program runs. In the beginning of the program, getting the required output was my biggest concern. Now I’m also starting to think about whether someone else could understand the code, what could happen with bad input, and how I’d check a change without breaking the entire thing. Revisiting this older project made this a lot easier to see the difference.

What I learned across the program

All my coursework has included databases, application design, mobile & full-stack development, and of course security. Working with SQL and MongoDB has made me aware that data storage choices affect the rest of an application. Application development brings the interface and program logic together, while the security coursework has brought me to think about what could gro wrong instead of only planning for the expected input. I want to keep building applications that are going to be useful to people and still easy to understand for the developers that help maintain them.

Most of my communication work in this class was outside of the dashboard itself. In my Module Two journal, I went over the code-review checklist covering the structure, documentation, variables, control flow, and defensive programming. I used an outline to organize the recorded review around the already existing program, the problems that I ran into, and the changes that I had planned. That helped me with explaining the reason for my enhancement instead of just simply reading the code out loud.

The Module Three journal also had me thinking about what belongs in a public portfolio. I discussed ownership, permission, and removing the credentials or any private information before sharing work. The journals afterwards gave me more practice explaining how technical development could affect users and my career. I felt these assignments were important because a developer needs to be able to explain consequences and the trade-offs to people who don’t have any technical background nor understand any of its jargon.

Collaboration and communication

It should be noted that this dashboard was created by me alone, so it does not serve as proof of my role of leading the development team. However, I can show how I managed to simplify the process of evaluation and transfer of the project. The configuration, access to data, rescue rules, and interface perform distinct functions. The README file helps to understand setup and restrictions of the project, and the tests allow for evaluating the changes from another developer's perspective. All of these options provide opportunities for teamwork as no prior understanding of the entire application is needed to make some contribution to its specific part.

I realized that I should change my approach to communication following the audience. A developer needs information about scoring rules, fields used in the query, and test results. An end-user needs to understand the meaning and limitations of the ranking. The suitability score is based on the course-project rules, and it does not provide any verified prediction on animals' rescue abilities. Both of these aspects are equally important. These are communication and collaborative skills I am able to show right now.

Design and algorithms

The software design enhancement separated a notebook-based project into a standalone Dash application. That made it easier to test the rescue rules and data access without putting every responsibility in the interface. CSV mode also lets someone run the dashboard without recreating the original course database environment. The work taught me to preserve useful behavior while changing the structure behind it.

For algorithms and data structures, I added suitability scoring and a bounded min-heap to choose the top five rescue candidates. I had to think about tied scores, missing values, and what to do when there are fewer than five matches. Selecting the top k candidates takes O(n log k) time for k greater than one, followed by O(k log k) to order the selected results. The heap uses O(k) extra space. That gives me a reason for the data structure beyond simply using something covered in class. I compared the complexity with sorting all N candidates, but I haven't claimed a measured speed improvement.

Databases and security

The database enhancements include the creation of generic read, create, update, and delete functions, including validation and indexing. An interesting thing to notice is that the column animal_id is not unique to this dataset since an animal may have multiple outcomes. Using the MongoDB _id during updates and deletion prevents multiple outcomes from being treated as a single record. Reads were done in a consistent order to ensure that the addition of an index doesn't change which tied entries come first.

The query comparison gave me concrete evidence to discuss. In the 10,000-record sample, each rescue query originally examined all 10,000 documents. With the rescue index, the Water, Mountain, and Disaster queries examined 18, 5, and 4 documents respectively, with the same results in the same order. That shows reduced query work in this test. It doesn't show a general speed multiplier, and the index still has storage and maintenance costs.

Security also became part of how I designed the application. Credentials stay outside the enhanced source code. New and updated values are checked, database errors don't expose connection details, writes are disabled by default, and deletion requires confirmation of the specific record ID. These checks reduce mistakes and unsafe input, but they aren't a replacement for database permissions or user authentication. A public service would need more access controls. Recognizing that boundary is part of the security mindset I want to keep developing.

How the portfolio fits together

The source artifact was taken from CS 340. It was used for all three enhancement types since each enhancement is a progression from the earlier one, meaning that the modular design allows for separate ranking tests, and the database use helps to control records and allow selective querying. Original code and milestones starting point is also provided in order to show how the changes have been made. The recorded code review outlines the original plan, and the narration describes what I learned during its execution.

All the artifacts are used to provide evidence for the five program outcomes: collaboration strategies due to readable modules and a handoff; oral, written, and visual communication due to the review, narrations, and dashboard; algorithm design due to the heap and query compromises, practical software development due to the actual application and testing; and security due to the validation, credentials management, and controlled writes. All my milestone submissions were awarded full points. For the portfolio completion, I made sure that my enhancements were within the scope and the wording and supporting artifacts were consistent.

My intention is to move on in software engineering and full-stack development. What I am good at is being able to divide a problem into parts, testing behaviors and justifying the choice of my solution. However, I am eager to gain more experience collaborating with other programmers and deploying applications for end users. Here I have an opportunity to start with something that I can talk about a functioning app, changes made and limitations that should be addressed.
