Milestone Two

Artifact Description

The artifact that I chose for the ePortfolio is my MongoDB CRUD Dashboard that I worked on in CS 340. It was originally created as an animal-shelter dashboard using Python, Dash, Pandas, Plotly, Dash Leaflet, and of course MongoDB. The application lets the user filter animals by rescue category, view matching records in a table, see the most common breeds within the chart, and view the selected animal’s location on the map.

Justification and Enhancement

I decided to use this artifact because it was using a few different parts of Software Development all within one project, like the user interface, application logic, data processing, and database access. It also gives me a chance to show how my development skills have improved since I originally created it. The original application worked for the class assignment but most of that code was only in the Jupyter Notebook. It also had database credentials that were directly in the code and needed in a .py file that I no longer have and didn’t know to save.

So, for this milestone, I mainly focused on the software design and the engineering portion that’s in the enhancement plan. I converted the notebook based project into a standalone Dash application and separated each of the responsibilities into different modules (Interface, rescue-filter logic, configuration, data access).

Since I moved the configuration outside of the main application source, I added validation and error handling, as well as making it able to run from the original CSV data outside of SNHU IDE. So now the project is more portable and easier to maintain. I wanted to be able to make sure that the refactor didn’t break the original functionality, with that in mind I added 6 automated tests and they all passed. I also tested Reset, Water Rescue, Mountain/Wilderness Rescue, and Disaster/Individual Tracking manually and saw that the table, breed chart, and the map all continued to update correctly.

Course Outcome Alignment

The enhancement supports the Outcomes (2, 4, 5) that were in my module one plan. For outcome 2 the project is a lot easier to explain and understand because the code is a lot more organized into easier to understand pieces. I also can communicate better with why each part of the application exists and how they work together.

For outcome 4 I used practices that I believe professional developers would use by turning the original prototype into a modular application and I also added reusable components, configuration handling, validation, and automated testing. You can see outcome 5 through the security improvements, the original project stored credentials directly in the main code, while the enhanced version now has configuration outside of the main source code and it handles errors and inputs with care. I don’t need to change my outcome plan for now but the later algorithm and the database milestone will help give me stronger evidence for the remaining technical areas.

Reflection on the Enhancement Process

I think the biggest thing that I learned from doing this enhancement is that my working code and maintainable code aren’t always the same thing. The original dashboard did what it needed to do for the assignment but after revisiting it, I could see how easily it could be improved. Breaking the project into smaller pieces lets me understand it easier, test, and organize and prepare for the changes that I plan to make in the future. The biggest issue that I’ve had is the missing .py file and how closely it was weaved into the course IDE. So, to learn from that mistake I made sure that it wasn’t going to be dependent on that setup and I made the enhanced version portable and self-contained while still behaving just like the original.
