Select the best few candidates

A suitability score and a bounded min-heap select the top five rescue candidates, with explicit tie handling and tests for edge cases.

Milestone Three Narrative

Artifact Description

For Milestone Three, I built upon the functioning version of Milestone Two and implemented an animal ranking system in it. The original version is present in the original folder, and the enhanced version is available in the enhanced folder.

Justification and Enhancement

I kept using this artifact because it already had a problem the algorithm could help solve. The filters returned animals that met the rescue requirements, but every matching record was treated the same. Adding a suitability score gives the dashboard a way to show which candidates rank highest under a set of rules. I put that logic in candidate_ranker.py so it can be tested separately from the interface.

The score is out of 100. It gives 20 points for animal type, 30 for breed, 20 for sex, 10 for being within the age range, up to 10 for being closer to the middle of that range, and 10 for valid coordinates. Since the rescue filters already check type, breed, sex, and age eligibility, most differences between eligible candidates come from the age bonus and location data. The midpoint preference is a simple rule for this course project, not a verified measure of rescue ability.

Python’s heapq library was employed to manage a min-heap with the top five candidates. Whenever the heap is full, the new candidate will replace the lowest-ranking candidate only if he or she ranks higher. In case of a tie, the order of the input list is maintained. The runtime complexity of selecting the top k from a list of n matching documents is O(n log k), assuming that k > 1, while the space complexity is O(k). After that, sorting of the selected k elements can be done in O(k log k). A sort of all candidates will run in O(n log n) time.

Reflection on the Enhancement Process

Another issue was how to use the scores when the records already met the rescue filter requirements. Scoring only on those criteria would make most people tie. The age bonus score creates a distinction within the acceptable bounds while keeping the criteria clear and simple. The weightings are important though, since a heap can still choose the largest values, but the scores will be based on criteria rules. Separating out the scoring from the rest of the algorithm makes the criteria rules simpler to change later.

The test suite expanded to 20 tests, all of which passed, even running from the extracted ZIP file. The tests include scoring, ordering, ties, empty records, missing fields, invalid k-values, and the Dash callback request. Browsing the dashboard tests were performed using the included CSV file data and covered all four filter options. Water results were 18 matching records and top 5 shown; Mountain results were 5 records and Disaster results were 4 records. The reset function clears the rankings and the preexisting table, chart, and map continue to work. The MongoDB live tests weren’t rerun for this milestone.

The trade-off was made clearer by the fact that the algorithm had a well-defined purpose in the dashboard. The enhancement in question is the ability to select the highest-scoring candidates from the matching records and then sort only those selected candidates. It should be noted that I haven’t timed any speed enhancement over sorting.
